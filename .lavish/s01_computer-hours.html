Incomplete periods no longer count

The first half of the request, implemented and tested before this page was written.

The artefact you spotted

Today is Monday. The calendar-week bucket for 2026-09-21 held one day of activity and was drawn, totalled and compared against seven-day weeks behind it:

week of 09-07139
week of 09-14221
week of 09-2127

Prompts per calendar week, real data. The last bar was not an 88% collapse — it was Monday morning.

Now: rolling 7-day blocks, recomputed daily. The strip no longer uses calendar weeks at all. Every block is seven whole days, the last one ending on the last complete day, so the comparison holds on any day of the week:

7 days to 09-06264
7 days to 09-13139
7 days to 09-20221

Same metric, same day, live from /api/trends?grain=week: ▲ 59% block-on-block where the calendar view showed a crash.

What changed

  • Weeks are rolling. _rolling() builds 26 blocks of exactly seven days each, anchored on the last complete day and recalculated every day — no Monday stub, ever. Each cell carries its own d → end, and the tooltip reads “7 days to 2026-09-20”.
  • Growth follows the same blocks: the last 7 days vs the 7 before, and the last 4 blocks vs the prior 4, so the tiles and the strips finally agree.
  • Days still show today, because seeing the day accumulate is useful — but it is drawn as a dashed outline, never a ramp colour, and is excluded from the row total, the active count, the colour scale, the sparkline and both growth figures.
  • The rolling tiles end yesterday: 7 complete days vs the 7 before, with today named in the lede instead of silently dragging the window down.
  • The API says so out loud: complete_through on /api/trends, as_of on /api/insights, done on every cell.
  • Three behaviour tests cover it, including one that asserts the blocks are seven days long and tile without gaps. 25 pytest + 4 vitest green.
The metric

One number: screen time

Exactly what the Screen Time panel puts at the top — hours the display was on and the Mac awake, per day. One strip, one tile, no app breakdown, no idle rules to argue about.

M-01 Screen time

Definition: minutes where the display is backlit and the machine is awake, bucketed into local days — the same thing Apple shows as “Screen Time” for this Mac.

Shape: a normal metric row like every other one. It formats as 8h 42m, gets a strip, a sparkline and block-on-block growth, and sits in METRICS beside prompts and commits.

Check: it is readable off System Settings → Screen Time, so it is verifiable by eye on any day. If we drift more than a couple of percent, the collector is wrong.

M-06 Output per hour derived

Nothing new to collect: output tokens, commits, PRs and agent $ divided by M-01. It is the reason to capture hours at all — a heavy day and a long day stop looking the same.

One extra ratio row, computed in the API from two numbers we already have.

Explicitly not in v1. Per-app hours, app categories, website domains, idle/active split, pickups and notification counts were all on the table and are all cut. They need either a permanent sampler or Full Disk Access, and each one raises a privacy question that a single hours number does not. The design below keeps the door open — they are additional event kinds on the same source — but nothing is built for them now.

The decision

Three ways to get that one number

Cutting the metric down to screen time cuts the options down with it. Costs are as visible as benefits on purpose.

O-B

pmset log

ship this

Parse pmset -g log for display on/off and sleep/wake transitions.

Gets you

  • M-01, exactly, from Apple’s own power log — the same transitions Screen Time counts.
  • Zero permissions: no Full Disk Access, no Accessibility prompt, no new daemon.
  • ~15 lines of parser, and it rides the 5-minute collector that already runs.
  • Keeps recording even when our collector is down — we just read the log afterwards.

Costs

  • 7-day retention: if the collector is off for longer than a week, those days are gone for good.
  • A text format, not an API — Apple could reword the lines, so the parser needs a fixture test and a loud failure.
  • No history before today beyond those 7 days.
O-A

knowledgeC.db

optional backfill

Apple’s own Screen Time store — /display/isBacklit gives the same metric.

Gets you roughly a month of screen-time history on day one, so the strip is not empty for its first 26 blocks — and a second opinion to reconcile the pmset parser against.

Costs a manual Full Disk Access grant in System Settings for whatever process reads it, and a tolerant reader for a private, undocumented schema that has changed between macOS releases. Retention is Apple’s call (~30 days), so it can only ever be a backfill, never the record.

Verdict: worth one afternoon if you want the back-history; skip it entirely and the metric still works from today onward.

O-C

Our own sampler

not needed now

A launchd job sampling frontmost app + idle every 60 s.

Gets you the things we just cut — per-app hours, idle/active split — at ~37 ms per sample and no permission grant.

Costs a permanent extra job and a stream of per-app events, to answer questions v1 is not asking. Cut — but the collector is written so this drops in later as one more event kind if you ever want the app breakdown back.

O-D

ActivityWatch

no

Costs a second daemon and a second event store for a number we can get in 15 lines; its default port 5600 is already taken by the DABStep-loop MLflow here; it captures window titles by default, which our own privacy rule forbids. Overkill for one metric.

O-E

Infer from events we already have

dishonest

Gets you a number today, free, back to February. Costs its meaning: it measures when agents were running, not when you were at the machine. Reading a PR, drawing a diagram or being in a call all read as zero. Fine as a QA cross-check, wrong as “screen time”.

Recommendation — O-B alone, with O-A as a one-off if you want the back-history. One metric, one parser, no permission grants, no new daemon. That is the whole build.
Proposed design

One parser, one strip

Deliberately boring: the new source lands in the same event stream, the same rollups and the same UI vocabulary as everything else.

Events

{"source":"screen","kind":"display_span", "ts":"2026-09-21T08:06:47Z","seconds":4621, "meta":{"src":"pmset"}} # a span crossing local midnight is split, so # every event belongs to exactly one local day {"source":"screen","kind":"display_span", "ts":"2026-09-20T13:58:00Z","seconds":120, "meta":{"src":"pmset","split":true}}

event_id = sha256("screen", "display_span", start_ts) — re-reading the same 7-day pmset window every 5 minutes produces identical ids, so the append-only store dedupes them exactly like every other source. No app names, no titles, no URLs: the entire payload is a start, a duration and a source tag.

Changes, module by module

  • schema.py — add "screen" to the Source literal and a seconds: float | None field (the first source that measures duration rather than counting things).
  • collectors/screen.py — new, ~15 lines of parsing plus span/midnight handling; an optional knowledge_spans() guarded by a readability check.
  • store/queries/daily.sql — one line: sum(seconds) AS seconds.
  • api/queries.py — one METRICS row (screen_hours) and one derived ratio (tok_out_per_hour).
  • Frontend — three lines: the key in METRIC_ORDER, and an hours formatter so it reads 8h 42m instead of 8.7.
  • No new launchd job, no new permissions, no enrich/ changes.

Before you say yes

Failure modes I expect

The 7-day window

pmset keeps about a week. If the collector stops for longer — laptop shelved, launchd job dies quietly — those days are unrecoverable, and the strip shows a hole rather than an error.

Mitigation: the collector records the log’s oldest timestamp each run, and the UI marks days where we know the log had already rolled past.

Clock and timezone

pmset prints local time with an offset; knowledgeC uses the 2001 Mac epoch; our events are UTC. Three clocks into one local-day bucket is exactly where an off-by-one day comes from.

Mitigation: every path normalises through schema.utc(), and a rollup test pins a midnight-crossing span to both days.

Sleep, lid, and external displays

“Display off” on a clamshell driving an external monitor does not mean you stopped, and dark wakes for backups look like usage.

Mitigation: dark wakes are filtered by assertion type; the hand reconciliation against Apple’s own panel is what catches the rest.

This Mac only

Screen Time aggregates across devices when syncing is on; we only ever see this machine, so our total reads lower than the panel if you use an iPad or a second Mac.

Mitigation: label the row “this Mac” rather than implying it is universal.

A text format, not an API

pmset -g log is human-readable output Apple has no contract to keep stable. A macOS upgrade could silently reword the lines and quietly zero the metric.

Mitigation: the parser fails loudly on an unparseable day rather than returning zero, and a fixture test pins today’s format.

Hours are a seductive number

A screen-time row invites optimising for the row: longer days look like better days, which is precisely backwards.

Mitigation: ship M-06 in the same change, so hours always appear next to output-per-hour rather than on their own.
